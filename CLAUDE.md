# Dungeon Designer

An ideation tool for dungeon layouts: a local web editor, a local server that owns the scene, and an MCP server so Claude Code can read and edit the same scene. See `plans/` for the vision (`00-initial`), and the finished phases (`01-first-playable` with `01B-first-playable-refinements`, `02-basic-3d-editing`, `03-UX-improvements`, `04-persistence`, `05-second-ux-improvements`, `06-more-shapes`). Phase `07-geometry-tools` (wall thickness, taper and bevel, tilt, holes, ramps; from `thinking-02-tweaking-shapes`) is built and was checked in the browser; its refinements are `07B-geometry-refinements` (fixes, an inspector panel, handles for walls, taper and bevel, drawing on surfaces, a view bar, isolate, lock and hide; done). The next phase is `08-semantics-and-entities` (from `thinking-03-semantics-and-entities`): an outline `get_scene` with `find_nodes` and an on-demand guide, a project library of tags and skills with a markdown design guide, notes, and entities (prefabs with their own history); 08.1 (the outline, `find_nodes`, the guide and group descriptions) 08.2 (the library: tags, skills and the design guide) 08.3 (notes) and 08.4 (entities: definitions, instances, Make entity, Detach) are built; Edit entity mode and the default human (08.5) are next. Phase 09 is the review loop (the agent renders the scene to check its own work; notes at the end of the 08 plan), and phase 10 is the array tool. Each phase plan logs its progress in a final Progress section. Use the terms in `GLOSSARY.md` when naming things, and add new terms there.

## Running

- `npm run dev` starts one process on http://127.0.0.1:5170 that serves the editor, the editor WebSocket (`/ws`) and the MCP endpoint (`/mcp`).
- **Start the server before starting Claude Code.** If the `dungeon-designer` MCP server shows as failed, start the server and reconnect with `/mcp`.
- The server saves everything in a **data folder**: `./data` where it runs (gitignored), or `DATA_DIR`. A lock file stops a second server from using the same folder.
- `PORT=5171 DATA_DIR=<scratch>/data npm run dev` runs a second instance for scripted checks. It must have its own `DATA_DIR`, so it never touches the main one's projects.
- `npm test` runs the unit tests, and `npm run typecheck` runs the type checker.

## Working with the scene

- To read or change the scene, use the `dungeon-designer` MCP tools (`get_scene`, `find_nodes`, `get_guide`, `get_library`, `update_library`, `make_entity`, `detach_instances`, `draw_shapes`, `update_nodes`, `remove_nodes`, `move_nodes`, `rotate_nodes`, `mirror_nodes`, `group_nodes`, `ungroup`). Don't edit files to draw. To repeat things, copy them with `move_nodes` and `copy: true` (`count` for a row) instead of redrawing them, and use `mirror_nodes` (world x or z) for symmetry. The core conventions are in the server's MCP instructions, and each shape type's detail is a `get_guide` topic (shapes, volumes, holes, ramps, lines, notes, groups, library, entities). `get_guide design` is the open project's own **design guide** (the human's taste, the game's facts and house rules): read it before designing.
- Coordinates are world units (`u` = meters), not pixels. The world is 3D with y up and the ground at y = 0. North is -z and east is +x (the **compass**, the same for every scene; the editor shows a compass rose). The scene holds **shapes**: boxes, cylinders, free-forms, lines, ramps and notes (`draw_shapes` takes a `type`, default `box`). A **note** (`note_N`) is a post-it pinned to a point (`x`, `y`, `z`), with `text` (which can refer to `@skills` and `#tags`), an optional `label` of up to 3 characters shown on its flag, a `color` (default yellow) and a `status`, `open` or `done`. The outline always lists the open ones (`notes`): treat them as the human's intent, and mark one done when it's handled rather than removing it. A **line** is an annotation: an open path of `points` in absolute world x/y/z (each with its own y; handles are 3D offsets), with `color`, `thickness` (screen px), `dashed` and `arrow`, and no kind, elevation or height. A **free-form** is a closed outline of `points` in absolute world x/z (bezier handles `in` / `out` are offsets from their point), with `y` and `height` but no center, size or rotation; moving, rotating and mirroring it change its points. To reshape a box or cylinder freely, convert it with `update_nodes { id, type: "freeform" }` (it gets a new ID). A **cylinder** has exactly a box's fields, and its footprint is the ellipse inscribed in width × depth; with `sides` (3–64) it's a regular polygon with a flat edge facing its local +x, and without, it's smooth. Every box, cylinder or free-form (a closed shape) is a room (hollow) or a volume (solid). A room's footprint is its outside, and its walls grow inward by `wall` (0.2 m by default). A volume can have `taper` and `bevel` (fractions 0..1: 1 = a pyramid or cone, 1 = a fully rounded top). A box or cylinder volume can tilt with `pitch` and `roll` (degrees around its own x and z axes, through its center; `y` stays the bottom before tilting). A third kind, **hole**, is any closed shape that cuts itself out of the shapes near it in the tree: for a hole in group G with parent P, the shapes directly in G, in P, and in G's and P's sibling groups (a hole outside any group cuts nothing), for doors, windows and floor holes. A **ramp** is a path with a width (ramps, stairs with `step`, landings, walkways, spiral stairs): its `points` are the centerline in absolute world x/z, each with the surface's height `y`, and the agent can give a `spiral` instead. A ramp is always a volume. A box's footprint is **centered** at `x, z`, with `width` along its local x and `depth` along its local z. It rises from its elevation `y` (its bottom: 0 = on the ground, negative = below) to `y + height`. `rotation` is in degrees around the vertical axis through the center, counterclockwise seen from above. `color` is a palette key, and `name` is an optional, non-unique label. IDs are `box_1`, `cylinder_1`, `freeform_1`, `line_1`, ..., never reused, and they're how the other tools refer to a node. Every tool call is one step in the undo history the human shares with the agent. The editor is a 3D view seen from a fixed pitch, rotating only by yaw.
- The scene's `nodes` is one flat list of boxes and **groups** (`group_1`, ...). A node is in a group when its `parent` is that group's ID. Groups have no position of their own: boxes keep absolute coordinates, and `get_scene` reports each group's derived `bounds` and `contains` (counts). A group can have a `description` (what that part of the level is), set with `update_nodes` or `group_nodes`. `get_scene` returns an **outline** by default: the top level (or a group's contents with `root`) down to `depth` levels, each collapsed group with its description, bounds and counts; `full: true` lists every node, and a scene of 40 nodes or fewer comes back in full. `find_nodes` looks nodes up by name, type, kind, group or place. To move or turn a group, use `move_nodes` / `rotate_nodes` on it (one call, one undo step). `rotate_nodes` turns around the bounds' center by default and returns that `pivot`; pass it back to turn something back exactly.
- The project has a **library** shared by its scenes: **tags** (`#climbable`, properties of things) and **skills** (`@telekinesis`, what the player can do, optionally acting on tags), plus the design guide. Groups, closed shapes and ramps carry `tags` (library names; a tag must exist first, via `update_library`). Descriptions refer to them as `@name` and `#name`, and `get_scene`'s `glossary` explains the ones it shows. A rename keeps the old name as an alias. Library edits have their own undo history, separate from the scene's.
- **Entities** are the project's prefabs: a name, a description, tags and a **definition** (its shapes around a pivot at the origin, its bottom center, in `entities/<id>/`). An **instance** (`instance_N`, `draw_shapes` type `instance`) places one at `x, y, z` with a `rotation`; its shapes, description and tags are the entity's, and `update_nodes` can swap its `entity`. For holes an instance is a group. `make_entity` turns shapes into an entity with an instance in their place, and `detach_instances` turns an instance back into a group. To repeat a thing, make it an entity and place instances.
- `scene.selection` lists the node IDs the human has selected in the editor, so "this" means those nodes. `view.isolated` is the node the human has isolated (only it and what's in it show), a node with `locked: true` can't be picked in the editor, and one with `hidden: true` (and what's in it) isn't drawn there (a hidden hole cuts nothing): human aids, so leave them alone unless asked.
- The scene's `view` is what the editor currently shows: `focus` (ground point at the screen center), `yaw` (degrees) and `bounds` (the axis-aligned box around the visible ground, `x, z` at its min corner). Before a browser connects it's focus 0,0, yaw 45, bounds -30..30 × -20..20.
- The scene is one **scene** of a **project**. The server has one open scene, shared by the editor and the agent; `get_scene` reports its `project` (with a description that gives the context) and `scene`. The human creates and opens projects in the editor. With nothing open, every tool returns an error saying so.
- Every edit is saved to disk as it happens. Don't read or edit files under `data/`: everything goes through the MCP tools or the editor, never raw file edits.

## Code layout

- `src/shared/`: types and zod schemas shared by the server and the editor, plus pure shape geometry (`geometry.ts`: every closed shape reduces to a footprint polygon, and each shape type's move / rotate / mirror / resize is one function there; concave room walls are offset with Clipper2, `@countertype/clipper2-ts`), the shape meshes (`mesh.ts`: every closed shape as watertight triangles, which rendering draws and picking and the marquee test), which holes cut what (`holes.ts`) and node-tree helpers (`tree.ts`).
- `src/server/scene.ts`: the scene store. It's the single code path for edits, used by both the WebSocket and MCP. Every edit goes through `commit` as one undoable command.
- `src/server/commands.ts`: ops, their inverses and the shared linear history (pure, no server dependencies).
- `src/server/persist.ts`: file access for the data folder (the lock, slugs, atomic JSON writes). `src/server/workspace.ts`: the open scene, which it loads into the store and saves after every step.
- `src/shared/library.ts`: the library's types, ops, references (`findRefs`) and alias resolution; `src/server/library.ts` its store (edits and its own history), `defaultGuide.ts` the design guide every project starts with. `src/server/outline.ts` is what the agent reads (the outline, the glossary, `find_nodes`), and `guide.ts` the core instructions and the `get_guide` topics.
- `src/shared/entities.ts`: the open project's definitions (a registry the server and the editor each set) and instances expanded into world shapes (a virtual group with IDs like `instance_4/box_2`; `ownerOf` maps back), which the geometry, rendering, picking and holes use.
- `src/server/{ws,mcp,main}.ts`: transports and wiring.
- `src/web/`: the React + three.js (react-three-fiber) editor. `camera.ts` holds the pure camera math, `gizmo.ts` the gizmo's and `points.ts` point editing's. `Inspector.tsx` is the floating panel with the selection's fields (the contextual bar keeps only kind and color). `csg.ts` cuts holes out of meshes with manifold (`manifold-3d`, WebAssembly, loaded in the background). `Library.tsx` is the Library panel and `RefText.tsx` the text areas that highlight and complete `@skill` / `#tag` references, and the tag chips. `errors.ts` is the tab's error log, shown by `ErrorPanel.tsx`, which also has the error boundaries.
