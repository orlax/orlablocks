# orlablocks

An ideation tool for dungeon layouts: a local web editor, a local server that owns the scene, and an MCP server so Claude Code can read and edit the same scene. See `plans/` for the vision (`00-initial`), and the finished phases (`01-first-playable` with `01B-first-playable-refinements`, `02-basic-3d-editing`, `03-UX-improvements`, `04-persistence`, `05-second-ux-improvements`, `06-more-shapes`). The next phase is `08-semantics-and-entities` (from `thinking-03-semantics-and-entities`): an outline `get_scene` with `find_nodes` and an on-demand guide, a project library of tags and skills with a markdown design guide, notes, and entities (prefabs with their own history); 08.1 (the outline, `find_nodes`, the guide and group descriptions) 08.2 (the library: tags, skills and the design guide) 08.3 (notes), 08.4 (entities: definitions, instances, Make entity, Detach) and 08.5 (Edit entity mode, the default human) are built; the phase's browser acceptance (§11 of the plan) is next. ## Running

- `npm run dev` starts one process on http://127.0.0.1:5170 that serves the editor, the editor WebSocket (`/ws`) and the MCP endpoint (`/mcp`).
- **Start the server before starting Claude Code.** If the `orlablocks` MCP server shows as failed, start the server and reconnect with `/mcp`.
- The server saves everything in a **data folder**: `./data` where it runs (gitignored), or `DATA_DIR`. `npm run dev` also reads a gitignored `.env` in the repo (e.g. `DATA_DIR=...`), and a variable set in the shell wins over it. A lock file stops a second server from using the same folder.
- `PORT=5171 DATA_DIR=<scratch>/data npm run dev` runs a second instance for scripted checks. It must have its own `DATA_DIR`, so it never touches the main one's projects.
- `npm test` runs the unit tests, and `npm run typecheck` runs the type checker.

## Working with the scene

- To read or change the scene, use the `orlablocks` MCP tools (`get_scene`, `find_nodes`, `get_guide`, `get_library`, `update_library`, `define_entity`, `make_entity`, `detach_instances`, `draw_shapes`, `update_nodes`, `remove_nodes`, `move_nodes`, `rotate_nodes`, `mirror_nodes`, `group_nodes`, `ungroup`, `transform_nodes`, `render_view`, `check_sight`, `check_enclosure`, `measure_path`, `check_scene`, `get_changes`, `get_shots`, `export_scene`). Don't edit files to draw. To repeat an entity many times (battlements, windows round a tower, pillars), draw one **array** (`draw_shapes` type `array`, `get_guide arrays`) instead of copies (a path array can follow a shape's outline, `layout.along`, so battlements stay on the wall top when the keep changes); to repeat other things, copy them with `move_nodes` and `copy: true` (`count` for a row) instead of redrawing them, and use `mirror_nodes` (world x or z) for symmetry. The core conventions are in the server's MCP instructions, and each shape type's detail is a `get_guide` topic (shapes, volumes, holes, ramps, lines, notes, groups, library, entities, arrays). `get_guide design` is the open project's own **design guide** (the human's taste, the game's facts and house rules): read it before designing. To see your work, `render_view` returns an image drawn by the open editor (a labeled `sheet` by default; `plan`, `node`, `eye`, `walk` along a line or ramp, a stored `shot` again, `shots`: the human's captioned shots as taken and now, since a captioned shot is a requirement, or `entities`: a model sheet), and `get_shots` lists the human's shots (with `id`, its image as taken). `check_sight` says in text whether targets are in view from eyes (points, nodes to stand on, or the walking human) and what blocks them, nearest first (`ignore` for decor), and `render_view`'s `hide` and `clip` (for that render only) show an enclosed room from outside. `get_guide review` is how to check work as a level designer; keep detail proportional to gameplay.
- Coordinates are world units (`u` = meters), not pixels. The world is 3D with y up and the ground at y = 0. North is -z and east is +x (the **compass**, the same for every scene; the editor shows a compass rose). The scene holds **shapes**: boxes, cylinders, free-forms, lines, ramps and notes (`draw_shapes` takes a `type`, default `box`). A **note** (`note_N`) is a post-it pinned to a point (`x`, `y`, `z`), with `text` (which can refer to `@skills` and `#tags`), an optional `label` of up to 3 characters shown on its flag, a `color` (default yellow) and a `status`, `open` or `done`. The outline always lists the open ones (`notes`): treat them as the human's intent, and mark one done when it's handled rather than removing it. A **line** is an annotation: an open path of `points` in absolute world x/y/z (each with its own y; handles are 3D offsets), with `color`, `thickness` (screen px), `dashed` and `arrow`, and no kind, elevation or height. A **free-form** is a closed outline of `points` in absolute world x/z (bezier handles `in` / `out` are offsets from their point), with `y` and `height` but no center, size or rotation; moving, rotating and mirroring it change its points. To reshape a box or cylinder freely, convert it with `update_nodes { id, type: "freeform" }` (it gets a new ID). A **cylinder** has exactly a box's fields, and its footprint is the ellipse inscribed in width × depth; with `sides` (3–64) it's a regular polygon with a flat edge facing its local +x, and without, it's smooth. Every box, cylinder or free-form (a closed shape) is a room (hollow) or a volume (solid). A room's footprint is its outside, and its walls grow inward by `wall` (0.2 m by default). A volume can have `taper` and `bevel` (fractions 0..1: 1 = a pyramid or cone, 1 = a fully rounded top). A box or cylinder volume can tilt with `pitch` and `roll` (degrees around its own x and z axes, through its center; `y` stays the bottom before tilting). A third kind, **hole**, is any closed shape that cuts itself out of the shapes near it in the tree: for a hole in group G with parent P, the shapes directly in G, in P, and in G's and P's sibling groups (a hole outside any group cuts nothing), for doors, windows and floor holes. A **ramp** is a path with a width (ramps, stairs with `step`, landings, walkways, spiral stairs): its `points` are the centerline in absolute world x/z, each with the surface's height `y`, and the agent can give a `spiral` instead (lines and path layouts take a `spiral` too, and a circle layout a `rise`, for spirals of platforms). A ramp is always a volume. A box's footprint is **centered** at `x, z`, with `width` along its local x and `depth` along its local z. It rises from its elevation `y` (its bottom: 0 = on the ground, negative = below) to `y + height`. `rotation` is in degrees around the vertical axis through the center, counterclockwise seen from above. `color` is a palette key, and `name` is an optional, non-unique label. IDs are `box_1`, `cylinder_1`, `freeform_1`, `line_1`, ..., never reused, and they're how the other tools refer to a node. Every tool call is one step in the undo history the human shares with the agent. The editor is a 3D view seen from a fixed pitch, rotating only by yaw.
- The scene's `nodes` is one flat list of boxes and **groups** (`group_1`, ...). A node is in a group when its `parent` is that group's ID. Groups have no position of their own: boxes keep absolute coordinates, and `get_scene` reports each group's derived `bounds` and `contains` (counts). A group can have a `description` (what that part of the level is), set with `update_nodes` or `group_nodes`. `get_scene` returns an **outline** by default: the top level (or a group's contents with `root`) down to `depth` levels, each collapsed group with its description, bounds and counts; `full: true` lists every node, and a scene of 40 nodes or fewer comes back in full. `find_nodes` looks nodes up by name, type, kind, group or place, and finds array items (`type: "item"`, or `under` an array). The edit tools return **compact results** (ids, bounds and counts; an array's **item lines**, `array_5/3 → x, y, z · top t · r°`), `verbose: true` for the full nodes. To move or turn a group, use `move_nodes` / `rotate_nodes` on it (one call, one undo step). `rotate_nodes` turns around the bounds' center by default and returns that `pivot`; pass it back to turn something back exactly.
- The project has a **library** shared by its scenes: **tags** (`#climbable`, properties of things) and **skills** (`@telekinesis`, what the player can do, optionally acting on tags), plus the design guide. Groups, closed shapes and ramps carry `tags` (library names; a tag must exist first, via `update_library`). Descriptions refer to them as `@name` and `#name`, and `get_scene`'s `glossary` explains the ones it shows. A rename keeps the old name as an alias. Library edits have their own undo history, separate from the scene's.
- **Entities** are the project's prefabs: a name, a description, tags and a **definition** (its shapes around a pivot at the origin, its bottom center, in `entities/<id>/`). An **instance** (`instance_N`, `draw_shapes` type `instance`) places one at `x, y, z` with a `rotation`; its shapes, description and tags are the entity's, and `update_nodes` can swap its `entity`. For holes an instance is a group. `define_entity` makes an entity from shapes given around its pivot (never drawn in the scene), `make_entity` turns shapes already drawn into an entity with an instance in their place (`keep: false`: none), and `detach_instances` turns an instance back into a group. In one `draw_shapes` call, an entry's `ref` lets later entries use `$ref` for `parent`, `layout.along.id`, `on.id` or stops, and a `group` entry makes a group with what's in it. An instance or array can stand `on` another node (an array on an array, item on item), and a line can go `through` stops (nodes, `array_3/*`, `array_3/2..6`) as jump arcs: both kept up to date, and unlinked by a hand edit. To repeat a thing, make it an entity and place instances, or one **array** (`array_N`): it repeats entities on a layout (a path, a circle, a grid or a scatter), live, and its items (`array_3/7`) are instances placed where the array is (for holes too); `detach_instances` turns it into a group of instances. In **Edit entity** mode (the human double-clicks an instance) the store holds the entity's definition with its own undo history, `get_scene` reports `editing`, and every change reaches every instance. Every project starts with a `human` entity, 1.8 m tall.
- `scene.selection` lists the node IDs the human has selected in the editor, so "this" means those nodes. `view.isolated` is the node the human has isolated (only it and what's in it show), a node with `locked: true` can't be picked in the editor, and one with `hidden: true` (and what's in it) isn't drawn there (a hidden hole cuts nothing): human aids, so leave them alone unless asked.
- The scene's `view` is what the editor currently shows: `focus` (ground point at the screen center), `yaw` (degrees) and `bounds` (the axis-aligned box around the visible ground, `x, z` at its min corner). Before a browser connects it's focus 0,0, yaw 45, bounds -30..30 × -20..20.
- While the human walks through the level (the Walk tool), `view.walking` is their eye, where it looks and the field of view.
- The scene is one **scene** of a **project**. The server has one open scene, shared by the editor and the agent; `get_scene` reports its `project` (with a description that gives the context) and `scene`. The human creates and opens projects in the editor. With nothing open, every tool returns an error saying so.
- Every edit is saved to disk as it happens. Don't read or edit files under `data/`: everything goes through the MCP tools or the editor, never raw file edits.

## Code layout

- `src/shared/`: types and zod schemas shared by the server and the editor, plus pure shape geometry (`geometry.ts`: every closed shape reduces to a footprint polygon, and each shape type's move / rotate / mirror / resize is one function there; concave room walls are offset with Clipper2, `@countertype/clipper2-ts`), the shape meshes (`mesh.ts`: every closed shape as watertight triangles, which rendering draws and picking and the marquee test), which holes cut what (`holes.ts`) and node-tree helpers (`tree.ts`).
- `src/server/scene.ts`: the scene store. It's the single code path for edits, used by both the WebSocket and MCP. Every edit goes through `commit` as one undoable command.
- `src/server/commands.ts`: ops, their inverses and the shared linear history (pure, no server dependencies).
- `src/server/persist.ts`: file access for the data folder (the lock, slugs, atomic JSON writes). `src/server/workspace.ts`: the open scene, which it loads into the store and saves after every step.
- `src/shared/library.ts`: the library's types, ops, references (`findRefs`) and alias resolution; `src/server/library.ts` its store (edits and its own history), `defaultGuide.ts` the design guide every project starts with. `src/server/outline.ts` is what the agent reads (the outline, the glossary, `find_nodes`), and `guide.ts` the core instructions and the `get_guide` topics.
- `src/shared/arrays.ts`: where an array's items go (`arrayItems`: its layout, facing, seeded noise and skips), and how moving, turning and mirroring an array change its layout (10.1).
- `src/shared/entities.ts`: the open project's definitions (a registry the server and the editor each set) and instances expanded into world shapes (a virtual group with IDs like `instance_4/box_2`; `ownerOf` maps back), which the geometry, rendering, picking and holes use.
- `src/server/shots.ts`: the open document's shots (09.1): images and records in its `shots/` folder, not in any history. `src/server/render.ts`: `render_view`'s go-between (09.3): it checks a request and asks the editor tab on screen that had focus last to render it.
- `src/shared/bake.ts`: a shape as the editor draws it (the **bake**: body and floor, holes cut, UVs, creased normals), which the view and the Unity export share; `csg.ts` the hole cuts (manifold, handed over by `src/web/csg.ts` in the browser and `src/server/manifold.ts` in Node), and `bakeScene.ts` a whole scene with each entity once. `src/server/export.ts` writes a scene for Unity (`level.json` and a mesh binary, in Unity's frame), `gltf.ts` the same as a `.glb`, `exports.ts` holds the project's Unity folder and exporting after every step, and `picker.ts` opens the system's folder dialog (15).
- `src/server/{ws,mcp,main}.ts`: transports and wiring (`main.ts` also serves the shot images).
- `src/ui/`: what the editor and the Control Panel share (12): the theme (`theme.css`: paper and ink, the block pastels, role tokens like `--accent`; light and dark), the bundled fonts (`fonts.css`), the `Wordmark`, the favicons, and `viewColors.ts` (the theme's colors for what the editor draws over the level). The 3D view's own colors (background, grid, palette) aren't theme colors.
- `src/web/`: the React + three.js (react-three-fiber) editor. `camera.ts` holds the pure camera math, `gizmo.ts` the gizmo's and `points.ts` point editing's, `arrayEdit.ts` an array's edit mode's. `Inspector.tsx` is the floating panel with the selection's fields (the contextual bar keeps only kind and color), and `EntityPicker.tsx` its searchable entity picker. `csg.ts` cuts holes out of meshes with manifold (`manifold-3d`, WebAssembly, loaded in the background). `Library.tsx` is the Library panel and `RefText.tsx` the text areas that highlight and complete `@skill` / `#tag` references, and the tag chips. `errors.ts` is the tab's error log, shown by `ErrorPanel.tsx`, which also has the error boundaries. `floating.ts` makes a panel draggable and collapsible (the inspector, Entities and Shots panels). `InstancedArrays.tsx` draws arrays' items instanced (which ones: `instancing.ts`). `capture.tsx` draws a clean capture of the scene on a canvas of its own that's never in the page (a react-three-fiber root drawn by hand, so it works in a background tab), and `ShotsPanel.tsx` is the Shots panel (`shots.ts` its pure parts). The Walk tool's math is `walk.ts` and its screens (HUD, pause menu, avatar) `WalkScreens.tsx`; the view runs the walk. `renderView.ts` draws the agent's renders from captures (labels, captions, a plan's grid and scale bar), planned in `renders.ts`.
